## 核心思想

大多数人与 LLM 和文档的交互方式类似于 **RAG**：上传文件，查询时检索相关片段，生成答案。这确实有效，但每次提问 LLM 都要从头重新发现知识——没有积累。需要综合多个文档的微妙问题时，LLM 每次都要重新寻找和拼凑片段。

> [!tip] 关键洞察
> **让 LLM 增量式构建和维护一个持久的 wiki** —— 不是临时检索，而是持续积累。

当你添加新资料时，LLM 会：
- 提取关键信息
- 更新实体页面
- 修订主题摘要
- 标记新旧数据的矛盾
- 维护交叉引用

**知识被编译一次，然后保持最新** —— 而不是每次查询都重新推导。

> [!quote] 本质区别
> **Wiki 是一个持久的、复利式的产物。** 交叉引用已经存在，矛盾已被标记，综合已反映你读过的所有内容。Wiki 随着你添加的每个来源和提出的每个问题而变得丰富。

## 三层架构

| 层级 | 说明 |
|------|------|
| **原始资料** | 你收集的文档（文章、论文、图片），LLM 只读不改 |
| **Wiki 层** | LLM 生成的 Markdown 文件（摘要、实体页、概念页），LLM 全权维护 |
| **Schema 层** | 配置文档（如 CLAUDE.md），定义 wiki 结构和约定 |

## 三种核心操作

### 1. 摄取（Ingest）

添加新资料，LLM 写入摘要、更新索引、维护相关页面。单个来源可能涉及 10-15 个 wiki 页面。

> [!example] 流程示例
> 1. LLM 读取来源
> 2. 与你讨论关键要点
> 3. 在 wiki 中写入摘要页面
> 4. 更新索引
> 5. 更新相关实体和概念页面
> 6. 在日志中追加条目

### 2. 查询（Query）

基于 wiki 回答问题，有价值的答案可归档回 wiki。

> [!important] 复利效应
> 比较、分析、发现的联系——这些都有价值，不应消失在聊天记录中。探索成果像摄取的来源一样在知识库中复利增长。

### 3. 清理（Lint）

定期检查：
- 页面间的矛盾
- 新来源取代的陈旧声明
- 无入站链接的孤立页面
- 提及但缺乏独立页面的重要概念
- 缺失的交叉引用
- 可用网络搜索填补的数据空白

## 两个关键文件

- **index.md** — 内容目录，列出所有页面和摘要
- **log.md** — 操作日志，按时间记录摄取、查询、清理等

## 实际应用场景

| 场景 | 描述 |
|------|------|
| 📔 **个人成长** | 追踪目标、健康、日记，构建自我结构化图景 |
| 🔬 **深度研究** | 阅读论文、报告，增量构建带有演变论点的综合 wiki |
| 📚 **读书笔记** | 为每章建立档案，构建角色、主题、情节线索页面。最终形成丰富的伴侣 wiki |
| 🏢 **团队知识库** | 基于 Slack、会议记录自动维护，LLM 执行无人愿意做的维护工作 |
| ✈️ **其他** | 竞争分析、尽职调查、旅行规划、课程笔记、爱好深入研究 |

## 与 [[Claude Code]] 的协作

> Obsidian 是 IDE；LLM 是程序员；wiki 是代码库。

在实践中：
- LLM Agent 开在一侧
- Obsidian 开在另一侧
- LLM 根据对话进行编辑
- 你实时浏览结果——跟踪链接、查看图谱视图、阅读更新后的页面

## 为什么有效

> [!quote] 核心洞见
> 维护知识库最枯燥的不是阅读或思考，而是繁琐的 bookkeeping —— 更新交叉引用、保持摘要最新、标记矛盾。人类会因此放弃 wiki，但 LLM 不会厌倦，不会忘记更新交叉引用，可以一次处理 15 个文件。

这本质上实现了 **Vannevar Bush 1945 年提出的 Memex 愿景**：一个私人的、精心策划的知识存储系统，文档之间的关联与文档本身同等重要。

---

> [!note] 灵活性
> 这是一个**理念框架**，而非具体实现。目录结构、Schema 约定、页面格式、工具——都取决于你的领域、偏好和 LLM 选择。挑选有用的，忽略无用的。
